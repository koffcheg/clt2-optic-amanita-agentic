## Definition

`inverse_median` - канонічний варіант етапу `radiometric_correction`, який
реалізує МКМФ: міжкадровий попіксельний медіанний фільтр лише по часу, без
просторового вікна, та формує різницевий кадр:

```text
Residual_t(x, y) = I_t(x, y) - Med_t(x, y)
```

де:
- `I_t(x, y)` - значення пікселя поточного кадру;
- `Med_t(x, y)` - міжкадрова медіанна оцінка фону для відповідного пікселя;
- `Residual_t(x, y)` - результат інверсної міжкадрової медіанної фільтрації.

Ця специфікація конкретизує канонічний варіант `inverse_median` етапу
`radiometric_correction`.

МКМФ формує фон/residual для подальшої обробки в конвеєрі. Медіанний
кадр, residual і користувацьке приведення residual є різними сутностями і не
повинні змішуватися.

## Scope

- Інтерфейс етапу: `IRadiometricStage`.
- Слот конвеєра: `radiometric_correction`; DSL-ключ: `radiometric`.
- Рівень складності: `L1`.
- Варіант: `inverse_median`.

Підтримувані режими:
- `FixedK3` - точна міжкадрова медіана за 3 відібраними кадрами;
- `FixedK5` - точна міжкадрова медіана за 5 відібраними кадрами.

## Inputs

- Вхідні кадри надходять послідовно у потоковому режимі.
- Вхідний формат - один канал, градації сірого.
- Підтримувані типи пікселя: `uint8` або `uint16`.
- Якщо у вхідному потоці застосовується бінування, МКМФ отримує фактичний формат
  кадру після бінування.

Вхідний домен:
- `dp1.domain.processing`.

Обмеження runtime-формату і типу входу:
- фактичний кадр після підготовки або бінування;
- один канал;
- `uint8` або `uint16`.

## Outputs

Медіанний кадр `Med_t` має формат фактичного вхідного кадру:
- для `uint8` вхідних кадрів - `uint8`;
- для `uint16` вхідних кадрів - `uint16`.

Residual формується у знаковому форматі підвищеної розрядності:
- для `uint8` вхідних кадрів - `int16`;
- для `uint16` вхідних кадрів - `int32`.

Вихід для наступних етапів:
- residual або скоригований processing domain для наступних етапів конвеєра.

Підтримувані режими представлення residual визначають тільки спосіб
представлення вже обчисленого residual.

`RawSigned` - residual повертається без приведення:
- `int16` для вхідного `uint8`;
- `int32` для вхідного `uint16`.

Цей режим рекомендований для внутрішніх обчислень конвеєра та для задач, де
важливо не втрачати слабкі сигнали. Він зберігає від'ємні значення і не втрачає
інформацію через обмеження діапазону.

`ClipToInputRange` - значення residual обмежуються діапазоном вхідного формату:
- для `uint8`: `[0, 255]`;
- для `uint16`: `[0, 65535]`.

Формула:

```text
Residual_clip(x, y) = min(max(Residual(x, y), 0), Imax)
```

Цей режим рекомендований для користувацького виходу за замовчуванням, оскільки
не змінює масштаб сигналу та зберігає локальний контраст у межах допустимого
діапазону. Недолік: значення за межами діапазону втрачаються через насичення.

`ShiftToPositive` - residual зсувається у додатну область:

```text
Residual_shift(x, y) = Residual(x, y) - min(Residual)
```

Режим корисний для візуалізації, але змінює базовий рівень сигналу. Може
потребувати попереднього пошуку глобального мінімуму, тобто додаткового проходу
по кадру.

`ScaleToInputRange` - residual масштабується до діапазону вхідного формату.

Для `ScaleToInputRange` значення residual множаться на коефіцієнт
масштабування:

```text
alpha = range_input / range_residual
```

де:
- `range_input` - діапазон вхідного формату;
- `range_residual` - динамічний діапазон residual.

У загальному вигляді:
```text
Residual_scaled(x, y) = alpha * Residual(x, y)
```

Метод гарантує стискання діапазону до масштабу вхідного формату, але може
зменшувати видимість слабкоконтрастних об'єктів. Він дорожчий за clipping,
оскільки потребує множення та приведення типу.

## Preconditions

- МКМФ є варіантом зі станом для `radiometric_correction`; стан належить реалізації
  `inverse_median`.
- Код legacy і legacy-reference cards не є джерелом цієї специфікації.

Обов'язкові ключі фрагмента конфігурації:
- `radiometric.enabled`;
- `radiometric.variant`;
- `radiometric.level`;
- `radiometric.parameters`;
- `radiometric.parameters.inverse_median.enabled`;
- `radiometric.parameters.inverse_median.mode`;
- `radiometric.parameters.inverse_median.stride`;
- `radiometric.parameters.inverse_median.output_median_frame`;
- `radiometric.parameters.inverse_median.output_dynamic_range_mode`.

Обов'язковий контекст і runtime-стан:
- глобальний лічильник кадрів `t`;
- циклічний буфер відібраних кадрів;
- стан медіанного кадру `Med_t`;
- стан валідності residual;
- поточний `stride`;
- вибраний шлях оновлення `FixedK3` або `FixedK5`.

Явне володіння змінним станом:
- стан циклічного буфера, `Med_t`, ознаки валідності residual і службових даних
  належить реалізації `inverse_median`.

Усі буфери для циклічного вікна, медіанного кадру та службових даних мають бути
виділені під час конструювання або `reset()`. Заборонено створювати нові масиви,
`std::vector`, `cv::Mat` або інші динамічні об'єкти в гарячому циклі
`processFrame`.

Якщо `inverse_median` вимкнено у конфігурації при старті програми, пам'ять під
циклічний буфер кадрів не виділяється.

## Deterministic flow

МКМФ працює каузально:
- майбутні кадри не використовуються;
- для обчислення медіани використовуються тільки поточний та попередні відібрані
  кадри;
- медіана оновлюється тільки на кадрах, що потрапили у медіанне вікно за
  правилом `stride`;
- після заповнення буфера residual видається для кожного вхідного кадру з
  використанням останньої обчисленої медіани.

1. Прийняти наступний потоковий кадр `I_t`.
2. Перевірити, чи кадр потрапляє у медіанний буфер за правилом `t % stride == 0`.
3. Якщо кадр відібраний, оновити циклічний буфер і перерахувати `Med_t` для
   `FixedK3` або `FixedK5`.
4. Якщо циклічний буфер ще не заповнений достатньою кількістю відібраних кадрів,
   повернути явну ознаку відсутності валідного residual.
5. Якщо `Med_t` валідний, сформувати `Residual_t = I_t - Med_t`.
6. Повернути внутрішній residual у `RawSigned` або виконати явне користувацьке
   приведення, якщо цього вимагає `output_dynamic_range_mode`.
7. Монотонно просунути глобальний лічильник кадрів `t`.

Для кожного кроку дозволені побічні ефекти обмежені станом реалізації
`inverse_median`: оновлення лічильника кадрів, циклічного буфера, `Med_t`,
ознаки валідності і опційного представлення виходу.

## Configuration contract

`inverse_median` належить до існуючого DSL-ключа `radiometric`:

```json
{
  "radiometric": {
    "enabled": true,
    "variant": "inverse_median",
    "level": "L1",
    "parameters": {
      "inverse_median": {
        "enabled": true,
        "mode": "FixedK3|FixedK5",
        "stride": 1,
        "output_median_frame": false,
        "output_dynamic_range_mode": "RawSigned|ClipToInputRange|ShiftToPositive|ScaleToInputRange"
      }
    }
  }
}
```

Правила:
- Відсутність `enabled`, `variant`, `level` або `parameters` на рівні етапу
  `radiometric` є помилкою конфігурації.
- Відсутність `parameters.inverse_median` є помилкою конфігурації для
  `variant = "inverse_median"`.
- Відсутні ключі всередині `parameters.inverse_median` отримують резервні
  значення:
  - `enabled = true`;
  - `mode = "FixedK3"`;
  - `stride = 1`;
  - `output_median_frame = false`;
  - `output_dynamic_range_mode = "RawSigned"`.
- Якщо `radiometric.enabled = true`, але `parameters.inverse_median.enabled =
  false`, варіант `inverse_median` не виконується.
- Невідомі ключі є помилкою конфігурації.
- Внутрішній вихід конвеєра за замовчуванням - `RawSigned`; рекомендований
  користувацький або compatibility-вихід - `ClipToInputRange`.

## Invariants

Функціональні інваріанти:
- майбутні кадри не використовуються;
- медіана оновлюється тільки на кадрах, що потрапили у медіанне вікно за
  правилом `stride`;
- після заповнення буфера residual видається для кожного вхідного кадру з
  використанням останньої обчисленої медіани.

`stride` - це крок відбору кадрів у часове медіанне вікно, а не крок пам'яті і
не OpenCV row stride. Кадр потрапляє у медіанний буфер, якщо він є кожним
`stride`-м кадром потоку. Очікуване правило для лічильника кадрів із початком
у `0`:

```text
t % stride == 0
```

Обмеження для `stride`:
- `stride >= 1`;
- `stride = 1` означає, що у буфер потрапляє кожний кадр;
- `stride = 2` означає, що у буфер потрапляє кожний другий кадр;
- `stride = 3` означає, що у буфер потрапляє кожний третій кадр.

`stride` може змінюватися під час роботи камери за явною командою контуру
адаптації або конфігураційного шару. Зміна `stride` має виконуватися через
окрему дію API, а не через неявну зміну вже збереженої конфігурації.

Політика зміни `stride` під час виконання:
- нове значення має задовольняти `stride >= 1`;
- встановлення поточного значення нічого не змінює;
- зміна значення зберігає вже виділені буфери, оскільки `stride` не змінює
  розмір кадру, тип пікселя або розмір медіанного вікна `K`;
- зміна значення скидає стан відібраних кадрів циклічного буфера, інвалідовує
  поточні `Med_t` і residual та повертає фільтр у стан прогріву;
- глобальний лічильник кадрів має залишатися монотонним і не скидається;
- після зміни кадри знову відбираються за правилом `t % stride == 0` з
  поточним значенням глобального лічильника `t`.

До заповнення циклічного буфера достатньою кількістю відібраних кадрів residual
не є валідним. Реалізація має повертати явну ознаку відсутності валідного
residual.

Медіанний фільтр сам не розширює діапазон яскравості: значення медіани належить
множині вхідних значень відповідного пікселя. Розширення діапазону виникає на
етапі віднімання `I_t - Med_t`, тому residual має знаковий тип підвищеної
розрядності.

Residual у `RawSigned` є основним внутрішнім представленням для конвеєра.
Приведення residual до `uint8` або `uint16` є окремим етапом і виконується
тільки для повернення результату користувачу, візуалізації, запису у файл або
передачі в модулі, що очікують формат вхідного зображення.

Внутрішній режим за замовчуванням для конвеєра - `RawSigned`.
Рекомендований користувацький або compatibility-вихід - `ClipToInputRange`.

Приведення residual до вихідного формату має складність `O(N x M)` і є окремим
проходом по кадру.

Орієнтовна вартість:
- `ClipToInputRange`: 2-3 операції min/max на піксель;
- `ScaleToInputRange`: множення та приведення типу, дорожче за clipping;
- `ShiftToPositive`: може потребувати пошуку глобального мінімуму, тобто
  додаткового проходу по кадру.

Для high-FPS режимів приведення формату слід виконувати тільки тоді, коли це
потрібно для користувача, візуалізації, запису у файл або інтеграції з модулем,
що очікує `uint8`/`uint16`.

Аномальні пікселі можуть збільшувати кількість екстремальних додатних або
від'ємних значень у residual і, відповідно, кількість значень, які будуть
обмежені при `ClipToInputRange`. Це впливає на значення виходу, але не повинно
впливати на час виконання медіанного ядра `FixedK3` або `FixedK5`.

Кількість операцій на піксель є фіксованою для `FixedK3` і `FixedK5`; час
виконання медіанного ядра не повинен залежати від статистики значень пікселів.
Шлях перерахунку медіанного кадру для `FixedK3` або `FixedK5` має вибиратися
під час конструювання, `reset()` або іншої явної ініціалізації. Реалізація не
повинна виконувати вибір між `FixedK3` і `FixedK5` всередині попіксельного
циклу.

## Failure cases

- Використання майбутніх кадрів або логіки centered-window.
- Видача residual тільки для відібраних кадрів замість поведінки
  hold-last-median.
- Приховане приведення signed residual до `uint8` або `uint16`.
- Змішування `Med_t`, внутрішнього residual і user-facing виходу.
- Динамічні алокації в `processFrame`.
- Неявна зміна `stride` без визначеної політики стану буфера.
- Продовження використовувати медіанний стан, набраний за попереднім `stride`,
  після зміни `stride` під час виконання.
- Вибір між `FixedK3` і `FixedK5` всередині попіксельного циклу.
- Втрата від'ємних значень residual через clipping у внутрішньому конвеєрі.

## Non-goals

- `ArbitraryK8bit`.
- `Centered`.
- `SelectedOnly`.
- Просторове медіанне вікно.
- Прийняття кандидатів, фільтрація об’єктів або фінальне вимірювання.
- Прихований внутрішній формат конвеєра `ClipToInputRange`,
  `ShiftToPositive` або `ScaleToInputRange`.
- Просторова операція OpenCV `medianBlur` як реалізація МКМФ.
- Генерація коду із матеріалів Технічного завдання без канонічних карток, цієї
  специфікації і конфігурації `C`.

## Validation hooks

Час обробки масштабується лінійно від кількості пікселів кадру.

Профілювати окремо:
- оновлення медіани на відібраному кадрі;
- формування residual;
- приведення residual до вихідного формату;
- вартість optional `Med_t`;
- сумарний час варіанта `inverse_median`.

Валідаційні вимоги винесені в окрему картку:
- `validation.dp1.radiometric_correction.inverse_median`.

Маршрут валідації має перевіряти:
- підтримку `FixedK3`;
- підтримку `FixedK5`;
- `stride = 1`;
- `stride = 2`;
- `stride = 3`;
- каузальне формування часового вікна;
- відсутність використання майбутніх кадрів;
- поведінку hold-last-median для кадрів, що не потрапили у буфер;
- невалідний residual до заповнення циклічного буфера;
- `Med_t` у форматі фактичного вхідного кадру;
- residual `uint8 -> int16`;
- residual `uint16 -> int32`;
- точну відповідність формулі `Residual_t = I_t - Med_t`;
- `RawSigned`;
- `ClipToInputRange`;
- `ShiftToPositive`;
- `ScaleToInputRange`;
- відсутність динамічних алокацій у `processFrame`, якщо це можна
  інструментувати;
- стабільну роботу на довгій послідовності кадрів;
- окреме профілювання оновлення медіани, формування residual і приведення
  формату.

## Source-of-truth and canonicalization safety

- Ця специфікація етапу є канонічним джерелом цільової архітектури.
- Поведінку runtime, збірки, конфігурації та протоколів потрібно окремо
  перевіряти за кодом і авторитетними файлами середовища, конфігурації та
  протоколів перед твердженнями про виконання.
- Якщо канонічна ціль і спостережувана runtime-поведінка розходяться, потрібно
  повідомити про невідповідність і запропонувати мінімальний scope
  синхронізації; не можна мовчки переписувати жодну зі сторін.

## Open questions

- Чи має вимкнення та повторне ввімкнення під час виконання зберігати пам'ять
  циклічного буфера і стан, скидати стан або бути непідтримуваним після старту.
- Точна сигнатура API залежить від майбутньої реалізації інтерфейсу етапу DP1.
- Чи має `ShiftToPositive` описувати тільки чистий зсув `R - R_min`, чи контракт
  повинен явно фіксувати фінальне обмеження при виведенні у `uint8`/`uint16`:
  `clamp(R - R_min, L, U)`.
- Чи має `ScaleToInputRange` використовувати поточну формулу `alpha * R`, чи
  повне min-max приведення signed residual до цільового діапазону:
  `(R - R_min) * (U - L) / (R_max - R_min) + L`.
