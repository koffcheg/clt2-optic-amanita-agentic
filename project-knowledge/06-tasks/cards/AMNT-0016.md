## Summary

Задача визначає мінімальний canonical package для DP1 domains, boundary structures і runtime/tile support objects перед stage-level code generation.

## Goal

Дати AI-кодеру і розробникам явні canonical domains, structures і runtime/tile support objects для кадру, контексту, pixel formats, processing payloads, masks, candidates, segments і measurements.

## In scope

- Уточнити canonical DP1 data domains у `project-knowledge/02-dp1/canonical/data_domains/`.
- Додати конкретні structures, які живуть у цих domains.
- Додати мінімальні tile-local execution support structures для майбутнього опису паралельності.
- Зареєструвати пакет у `DP1_CANONICAL_INDEX.md`.
- Тримати structures окремо від algorithms.
- Зберегти canonical route: `Code = f(Cards, Stage_Spec, C)`.

## Out of scope

- Без production code changes.
- Без змін у `datapro1_v2`.
- Без змін у CMake/build/Docker/tests/.vscode.
- Без переписування stage specs або stage cards.
- Без реалізації повного parallel pipeline.
- Без створення нового folder `data_structures/`.

## User constraints

- Використати існуючий `data_domains/` folder замість паралельного structure folder.
- Розділити domains і concrete structures, прив'язані до цих domains.
- Трактувати 8-bit / 16-bit / F32 як pixel format / route-level properties.
- Тримати structures окремо від algorithms.
- Додати `FrameContext` як runtime/context object окремо від `FramePacket`.
- Додати мінімальні tile-local execution structures: `TileDesc`, `TileContext`, `TileResult`.

## Source access rules

Тільки canonical development. Legacy access для цієї задачі заборонений.

## Assumptions

- Існуючий `data_domains/` є правильним canonical location, бо він уже входить у source route в `DP1_CANONICAL_INDEX.md`.
- Existing `raw`, `processing`, `mask`, `measurement` domain cards треба уточнювати, а не дублювати.
- Точний C++ structure layout має визначатися окремою implementation task.
- Tile-local execution structures є target execution-support cards, а не claim про поточний runtime.

## Relevant context to read

- `project-knowledge/02-dp1/canonical/DP1_CANONICAL_INDEX.md`
- `project-knowledge/02-dp1/canonical/pipeline/dp1.pipeline.stage_contract.md`
- `project-knowledge/02-dp1/canonical/configuration/dp1.config.pipeline_configuration_c.md`
- `project-knowledge/04-protocols/cards/protocols.dp1_dp2.measurement_handoff.md`

## Planned changes

- Уточнити domain cards: Raw/Input, Processing, Mask, Struct, Measurement.
- Додати domain-bound structures: `FramePacket`, `ProcessingFrame`, `BinaryMask`, `Candidate`, `Segment`, `MeasurementRecord`.
- Додати runtime support structures: `FrameContext`, `TileDesc`, `TileContext`, `TileResult`.
- Додати stage-domain binding matrix, щоб AI-кодер бачив дозволені input/output domains для кожного stage.
- Оновити DP1 canonical index і task index.

## Files expected to be touched

Перелік файлів наведено в `related_files`.

## Risks

- Надмірно деталізувати implementation details до code tasks.
- Продублювати existing raw/processing/mask/measurement domain cards.
- Змішати algorithm details із data-domain cards.
- Переплутати target tile-local execution support із уже реалізованим parallel runtime.

## Validation approach

Knowledge-only review:
- перевірити, що code/build/test files не змінені;
- перевірити, що `data_structures/` folder не створений;
- перевірити, що domains і structures зареєстровані в `DP1_CANONICAL_INDEX.md`;
- перевірити, що stage-domain bindings обмежують дозволені input/output structures;
- перевірити, що cards не містять current-runtime claims, якщо вони не позначені як assumptions/open questions.

yes — canonical DP1 domain/structure package, stage-domain bindings і index оновлені.
