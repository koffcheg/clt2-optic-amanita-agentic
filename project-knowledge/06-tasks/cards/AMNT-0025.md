## Summary

Prepare canonical DP1 v2 domain carrier headers and one interface header per semantic pipeline stage.

## Goal

Provide code skeleton types for future code generation using canonical `data_domains` structures and stage contracts, without implementing variants, stubs, factories, or runtime execution.

## In scope

- Add canonical domain carrier headers under `datapro1_v2/include/dp1v2/domain/`.
- Replace the current DP1 v2 frame packet/context shape with canonical `FramePacket` and `FrameContext`.
- Add shared stage infrastructure types.
- Add one interface header per canonical DP1 stage.
- Keep full-frame and tile route input/output types explicit.

## Out of scope

- Concrete stage variants.
- Stub/no-op implementations.
- Pipeline executor, factory, registry, or `process_single_frame` integration.
- New automated tests, fixtures, mocks, or test infrastructure.
- Legacy-driven structure design.

## User constraints

- Use only canonical structures from `data_domains`.
- Existing `dp1_v2` legacy-shaped structures should be replaced by canonical structures where touched.
- Do not mix interfaces and concrete variants.
- Do not create stubs.
- Do not integrate with the pipeline yet.
- Each stage must be in a separate file; no monolithic `stages` file.

## Source access rules

Canonical development only. Legacy cards and legacy code are forbidden as design sources. Existing DP1 v2 code may be read only to preserve build compatibility while replacing touched structure shapes.

## Assumptions

- Stage interfaces can depend on canonical `StageConfig` from `PipelineConfig C`.
- Runtime bridge code may still convert canonical context to existing result output until a later approved migration replaces output contracts.
