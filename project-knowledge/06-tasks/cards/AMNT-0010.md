## Summary

Prepare Project Knowledge for card-driven / LLM-first development of canonical DP1 and future canonical DP2.

The task separates legacy-reference knowledge, canonical target knowledge, governance rules, protocol boundaries, and validation knowledge so that legacy DP1/DP2 cannot be mistaken for target canonical architecture.

## Goal

Produce a PK structure where:
- canonical DP1 has its own entry point, data-domain cards, stage-interface cards, configuration model `C`, complexity levels, and validation route;
- DP2 has canonical/legacy separation prepared without a full DP2 design;
- legacy cards remain reference material and are not sources of truth for canonical code;
- governance defines the card-driven route, task-card-controlled legacy access, and `Code = f(Cards, Stage_Spec, C)`.

## In scope

- Create physical `canonical/` and `legacy/` sections under `02-dp1/` and `03-dp2/`.
- Add canonical DP1 product, pipeline, data-domain, stage-interface, configuration, validation, and roadmap placeholders.
- Add canonical DP2 placeholders.
- Add or update the canonical DP1 -> DP2 protocol boundary in `04-protocols/`.
- Add or update validation knowledge for canonical DP1 conformance.
- Minimally update existing templates/governance files for required metadata and access rules.
- Classify existing DP1/DP2 cards as legacy-reference in legacy indexes or metadata/status.
- Normalize agent-facing Project Knowledge documentation to English.

## Out of scope

- Any production code changes.
- DP1/DP2 refactoring.
- New DP1 implementation.
- Full stage specifications.
- New root README.
- `AGENT_RULES.md`.
- New DP1/DP2-local card templates.
- Moving task cards into DP1 or DP2.
- Large rewrite of `CODE_STYLE.md`.
- DP1-only OpenCV policy.

## User constraints

- Work only with Project Knowledge and `AGENTS.md`.
- Do not change project source code.
- Do not create a new DP1 implementation.
- If an existing document already has the required role, update it instead of creating a duplicate.
- Task cards remain under `project-knowledge/06-tasks/`.
- Legacy is not a target-architecture source.
- Code must not be generated from informal text or legacy code.
- English is the canonical language for agent-facing documentation.
- Keep Russian or Ukrainian only for human-facing notes or explicitly bilingual fields such as `title.uk` / `title.en`.
- If meaning is unclear, write `TODO: confirm with user`.

## Assumptions

- Current `02-dp1/cards/*.md` and `03-dp2/cards/*.md` mostly describe existing code and should be treated as legacy-reference unless proven otherwise.
- Canonical DP1 in this task is an architecture/specification layer, not an implementation plan.
- The DP2 canonical section is a skeleton for future content.
