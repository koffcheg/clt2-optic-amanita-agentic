## Summary

Потрібно сформувати стандартний workflow для AI-агента, який самостійно виконує тест-рани Amanita+Comparator, зупиняється на помилках, зберігає артефакти у передбаченій структурі, та формує звіт за результатами.

## Goal

Забезпечити відтворюваний і керований тестовий процес:
- єдина структура run-директорій у `AmanitaResources/tests`
- універсальні скрипти запуску для Amanita і Comparator
- підготовлений пул релевантних датасетів із ground truth у `AmanitaResources/datasets/raw`

## In scope

- Формалізація структури test run і послідовності кроків у knowledge base.
- Перенесення/допрацювання універсальних скриптів запуску в репозиторій (`test.agent/scripts`).
- Інвентаризація Comparator resources та перенесення релевантних dataset+GT наборів у `AmanitaResources/datasets/raw` за типами.
- Підготовка бази для подальшого еталонного тестування Amanita незалежно від конкретної feature-задачі.

## Out of scope

- Зміни коду Comparator або OverlayRunner.
- Масові архітектурні рефакторинги у production-модулях.
- Додавання нових зовнішніх бібліотек.
- Виконання фактичного еталонного тест-рана без окремого підтвердження змісту звіту.
- Спеціалізація pipeline під окремий feature-сценарій (наприклад, бінування).

## User constraints

- Працювати з remote-гілками; робоча гілка задачі: `AMNT-0005` від `develop`.
- Comparator і OverlayRunner не змінювати (лише читати/використовувати як допоміжні).
- У межах AMNT-0005 не вносити зміни, пов'язані з бінуванням, і не додавати згадки про бінування у шаблони конфігів.
- Amanita за замовчуванням тестується як єдиний stage з DP1+DP2; окреме тестування модулів лише за явним узгодженням.
- Кожен test run має бути в окремій папці під `AmanitaResources/tests`.
- Обов'язкова структура run: `Configs`, `RunResults`, `Temp`, звіти у корені run.
- Для кожного `StageId` мати окремі піддиректорії в `Configs/Amanita/DP1`, `Configs/Amanita/DP2`, `Configs/Comparator` і `Logs/*`.
- Кроки виконання строго послідовні: config -> Amanita -> validate -> Comparator -> validate -> analysis/report.
- На будь-якій помилці зупинка та фіксація причини, далі очікування вказівок.
- Універсальними мають бути щонайменше скрипти запуску Amanita і Comparator.
- Скрипти зміни конфігів мають бути per-run і зберігатися у `Temp`.
- Додаткові універсальні скрипти тільки після окремого узгодження.

## Assumptions

- Ресурсний корінь визначається через `${AMANITA_RESOURCES_DIR}` згідно repo policy.
- Релевантним датасетом вважається набір, де одночасно присутні raw-дані (відео або кадри) і ground truth JSON.
- Перенесення датасетів у `AmanitaResources` є операційною дією поза git-репозиторієм і не створює commit-диф у коді.
