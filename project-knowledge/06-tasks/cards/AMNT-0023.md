## Summary

Replace the legacy-shaped `dp1_v2` configuration model with the canonical DP1
application and pipeline configuration model, including parsing and validation.

## Goal

`dp1_v2` must load typed canonical configuration from two separate files:
`ApplicationConfig` JSON and `PipelineConfig` JSON. Legacy and combined
authoring shapes must be rejected during normal parsing.

## In scope

- Canonical configuration DTOs and enums.
- JSON parsing for separate canonical application and pipeline config files.
- Validation for required sections, supported enum values, numeric ranges,
  stage keys, stage variants, levels, generic stage `parameters`, and resolved
  `inverse_median` parameters.
- Replacement of the bundled `datapro1_v2` sample config with two canonical JSON files.
- Minimal local consumer adaptation needed for build consistency.

## Out of scope

- DP1 algorithm implementation changes.
- Runtime pipeline architecture changes outside configuration plumbing.
- DP1 -> DP2 protocol redesign.
- New dependencies or test infrastructure.
- Automated unit test implementation.
- Broad Project Knowledge synchronization beyond this task card.

## User constraints

- Implement only local configuration changes.
- Do not use legacy materials as source for canonical code generation.
- Unit tests are a follow-up task; this task may only plan them.
- Stage registry names must follow `PipelineConfig C` keys:
  `prep`, `radiometric`, `enhancement`, `matched_filter`,
  `candidate_extraction`, `segmentation`, `object_filtering`, `measurement`.

## Source access rules

Canonical development mode. Legacy access is forbidden.

## Assumptions

- The canonical implementation uses two JSON files: one `ApplicationConfig` root
  and one `PipelineConfig` root.
- Full stage-interface card names remain knowledge/card identifiers, but config
  keys are the `PipelineConfig C` DSL keys listed above.
- Existing runtime consumers may temporarily use only the subset of the typed
  canonical config they need to run.
