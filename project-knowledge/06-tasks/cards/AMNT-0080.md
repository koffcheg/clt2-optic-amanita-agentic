## Summary

Implement the `TilePipeline` orchestration skeleton for the DP1 v2
`prep.variant = "tiles"` route.

## Goal

Route completed `PrepTilesOutput` through `TileTask[]`, oneTBB `TileExecutor`,
`TileProcessor`, `TileFrameAggregator`, and frame-level `FrameContext` summary
without worker-thread writes to shared frame state.

## In scope

- Add `TilePipeline` header and implementation.
- Pass typed tile execution and aggregation config explicitly from
  `ResolvedPipelineConfig::prep.tiles`.
- Update `process_single_frame` to receive raw and resolved pipeline config and
  route pipeline dependencies.
- Replace the downstream-not-connected tile branch with `TilePipeline` dispatch.
- Keep full-frame behavior on the existing `FullFramePipeline`.
- Add focused tests if needed.

## Out of scope

- Per-tile inverse median state ownership.
- New JSON fields or raw config reparsing.
- Serial fallback, backend dispatch, OpenMP, or custom thread pools.
- Required tile image merge/stitching.
- Per-tile logging or profiling switches.
- Domain Project Knowledge changes.

## User constraints

- Source of truth for tile execution and aggregation is
  `ResolvedPipelineConfig::prep.tiles`.
- `TilePipeline` must receive `PrepTilesParametersConfig` explicitly.
- Do not reparse `PipelineConfig::stages.prep.parameters`.
- Do not create default tile execution or aggregation config inside
  `TilePipeline`.
- Keep `TileExecutionSummary` in `TilePipelineResult`.
- Tests are approved if needed.

## Source access rules

Canonical development only. Legacy implementation sources and legacy-reference
cards are forbidden for code generation.

## Assumptions

- Current oneTBB executor class is named `TileExecutor`.
- `RadiometricStage` tile overload may still return `Unsupported` for
  `inverse_median` until a later per-tile state task.
- Existing result sink can publish an empty result only after successful
  aggregation; unsupported tiles must not become fake completed frames.

## Execution notes

Task card creation and tests were approved by the user on 2026-05-24.

## Result

Implemented `TilePipeline` with explicit typed tile config flow from
`ResolvedPipelineConfig::prep.tiles`, including:

- `TilePipelineArgs` with raw `PipelineConfig`, `ResolvedPipelineConfig`, and
  explicit `PrepTilesParametersConfig`;
- `TilePipelineResult` carrying lifecycle, sink, execution summary, and
  aggregation summary;
- pre-executor consistency validation for tile/view count, tile ids, image
  payloads, geometry, and valid areas;
- deterministic `TileTask[]` construction and pre-sized `TileResult[]`;
- oneTBB `TileExecutor` invocation through `args.tiles_config.execution`;
- `TileFrameAggregator` invocation through `args.tiles_config.aggregation` and
  `args.tiles_config.execution`;
- frame-level-only `FrameContext` summary writes after execution;
- runtime dispatch from `process_single_frame` through route-level
  `FullFramePipeline` and `TilePipeline`;
- controlled failure when resolved prep tiles config is missing;
- controlled unsupported tile-route failure while inverse-median per-tile state
  remains unimplemented.

Updated tests:

- pipeline tile route now verifies executor/aggregator-backed unsupported
  radiometric tile route instead of downstream-not-connected;
- added `TilePipelineTest` for tile/view count mismatch before executor.

Validation passed:

- `cmake --build build-dp1v2-tests --target dp1v2_unit_tests`
- `./build-dp1v2-tests/dp1v2_unit_tests`
- `cmake --build build-dp1v2-tests --target datapro1_v2`

Code search found no raw `ParameterMap` parsing in `TilePipeline`, no serial or
backend tile route, no tile-pipeline logging, and no worker-path
`FrameContext` access in `TileProcessor` / `TileExecutor`.
