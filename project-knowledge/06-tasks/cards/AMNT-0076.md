## Summary

Add the minimal tile-level result/status runtime model needed for future tile
execution and aggregation.

## Goal

`TileResult` can represent completed, skipped, disabled, unsupported, and failed
tile outcomes and can carry tile-local statuses, diagnostics, and timings without
requiring writes to shared `FrameContext` from worker threads.

## In scope

- Add `TileResultStatus`.
- Extend `TileResult` with status, error information, diagnostics, stage statuses,
  and stage timings.
- Extend `TileContext` only if needed for lightweight tile-local status/timing
  capture.
- Reuse existing domain structures and status/profiling types.

## Out of scope

- Implementing `TileProcessor`.
- Implementing `OneTbbTileExecutor`.
- Implementing tile radiometric execution.
- Adding frame-level side effects from tile workers.
- Adding new logging/profiling levels or tile-specific switches.
- Creating new large domain models.
- Changing full-frame behavior.

## User constraints

- Do not change Project Knowledge outside task-card workflow without approval.
- Do not use legacy code.
- Do not add serial tile fallback or execution backend fields.
- Do not write to `FrameContext` from future oneTBB worker threads.
- Do not add tile-level logging.
- Do not add automated tests without explicit approval from testing policy.

## Source access rules

Canonical development only. Legacy access is forbidden for this task.

## Assumptions

- Existing `Candidate`, `Segment`, `ValidatedObject`, and `MeasurementRecord`
  types are the domain vectors for `TileResult`.
- Existing `StageStatus`, `DiagnosticMessage`, and `StageTiming` are the runtime
  status/profiling structures to reuse.
- `StageStatusCode::NotStarted` has no exact completed tile-result equivalent.
