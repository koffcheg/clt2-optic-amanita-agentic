## Summary

Оновлено виконання DP1_v2 так, щоб порядок був строго від загального до часткового: спочатку Phase 0 runtime skeleton, потім алгоритмічна міграція/розширення.

Уточнення від 2026-04-21: `Phase 0` більше не трактується як лише bootstrap + config foundation. Робочий scope Phase 0 зафіксовано в `PHASE_0_RUNTIME_SKELETON.md`: `datapro1_v2` має стати повноцінним runtime-каркасом DP1 із зовнішньою сумісністю, але без алгоритмічної parity.

## Goal

Зафіксувати обов'язкову prerequisite-послідовність і довести Phase 0 до production-shaped runtime skeleton перед відновленням алгоритмічних підзадач.

## In scope

- Додати в план окрему передфазу Phase 0 (bootstrap + config foundation).
- Вести Phase 0 за уточненим runtime skeleton scope з `PHASE_0_RUNTIME_SKELETON.md`.
- Перебудувати checklist і phase grouping під порядок general -> specific.
- Оновити execution quickstart invariants/checklists під Phase 0-first.
- Оновити phase tracker (active phase, current iteration focus, parked artifacts).
- Додати changelog entry і оновити tasks index.
- Реалізувати базовий config-layer у `datapro1_v2` на основі мінімального піднабору legacy config.
- Прибрати test/debug startup behavior із runtime entrypoint.
- Підготувати каркас `datapro1_v2` до повного frame-level lifecycle: source runner, stage-by-stage pipeline boundary, порожній валідний `TDataRes`, DP1->DP2 send boundary і сумісні результатні artifacts.
- Врахувати CPU resource constraints через bounded queues / worker ownership / telemetry extension points без реалізації повного QoS.
- Зберегти DP1 як незалежний standalone-процес, сумісний із майбутнім зовнішнім orchestrator-ом без orchestrator-specific API всередині DP1.

## Out of scope

- Повний перенос усіх legacy config полів у DP1_v2.
- Зміни DP1->DP2 schema/message-id/serializer/transport.
- Будь-які зміни legacy DP1 runtime path.
- Реалізація повного QoS/autotune/backend policy.
- Реалізація network scheduler, distributed processing protocol або orchestrator-specific API всередині DP1.
- Алгоритмічна parity segmentation/measurement із legacy DP1.

## User constraints

- Спочатку обов'язкові попередні кроки (запуск і конфігурація), потім повернення до раніше розпочатих алгоритмічних кроків.
- Мінімальні локальні зміни у межах планувальних документів.
- Не змінювати контракти обміну DP1->DP2.
- Для довгоживучого runtime кожна порція даних має доходити до кінця frame-level pipeline або отримувати явний terminal status.
- Каркас має враховувати використання процесорного ресурсу, але не реалізовувати повний QoS у Phase 0.
- DP1 може бути не один і може керуватися майбутнім зовнішнім orchestrator-ом, але сам DP1 не повинен знати про це керування.

## Code review notes

- 2026-04-21: DP2 connect lifecycle risk залишено як accepted residual risk без виправлення. `datapro1_v2` викликає reused legacy `init_connect_to_dp2(...)` перед входом у source/runtime loop, що відповідає legacy DP1 startup order і не змінює DP1->DP2 schema/message-id/serializer/transport. Якщо DP2 endpoint fail-fast, runtime продовжує роботу з legacy reconnect behavior; якщо DNS/network timeout повільний, startup може затриматися до початку приймання кадрів. Для Phase 0 runtime/DP2 integration testing бажано піднімати DP2 заздалегідь або використовувати local fail-fast endpoint. Окремий timeout-aware v2 transport adapter потребує окремого погодження.
