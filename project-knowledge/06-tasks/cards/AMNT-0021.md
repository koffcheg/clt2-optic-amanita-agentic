## Summary

Create canonical profiling governance and DP1 profiling knowledge so weak profiling placeholders are replaced by explicit canonical structures and references.

## Goal

Move profiling-specific knowledge into `PROFILING_POLICY.md` and
`dp1.domain.profiling`, update dependent cards to reference the profiling card,
add detailed application profiling configuration, and decompose application
runtime configuration into child cards.

## In scope

- Create a profiling governance policy from the approved draft.
- Create canonical DP1 profiling data-domain card.
- Replace weak `StageTiming`, `StageProfile`, `ProfileEvent`, and `TileProfilingSummary` definitions with references to profiling structures.
- Add detailed `ApplicationConfig.profiling`.
- Decompose `ApplicationConfig` details into child cards for logging and
  profiling.
- Update canonical runtime, configuration, stage, validation, and index references.

## Out of scope

- Production C++ implementation.
- Automated tests, fixtures, benchmark infrastructure, or external profiler integration.
- Legacy analysis or legacy-source use.
- DP2 profiling model beyond references already present in governance text.

## User constraints

- Do not analyze legacy information.
- Treat the document as canonical.
- Files of type `_POLICY` must be in English.
- Cards must be Ukrainian except section names described by templates.
- External profiling tools are allowed only by separate explicit instruction.

## Source access rules

Canonical development only. Legacy access is forbidden.

## Assumptions

- `ApplicationConfig` is the correct runtime configuration surface for profiling controls.
- `PipelineConfig C` may reference profiling requirements but must not own operational profiling switches.
- Core DP1 stage ids come from `dp1.config.stage_variant_registry`, but profiling stage identifiers must remain extensible.
