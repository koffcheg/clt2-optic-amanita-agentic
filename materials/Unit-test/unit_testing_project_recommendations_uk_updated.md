# Рекомендації з юніт-тестування для конкретного проєкту комп'ютерного зору

## 1. Загальна позиція

Для проєкту доцільно прийняти GoogleTest як основний фреймворк юніт-тестування C++-коду. Тестування має бути організоване так, щоб швидкі юніт-тести перевіряли окремі алгоритмічні частини, а повні запуски DP1, DP2, Docker-сценарії, обробка реальних послідовностей кадрів і порівняння результатів експериментів були винесені на рівень інтеграційних, регресійних або performance tests.

Основна ціль на першому етапі - не створити максимальний відсоток coverage, а зафіксувати стабільну очікувану поведінку критичних частин pipeline: обробку кадрів, фрагментацію, перетворення типів, формування масок, розрахунок координат, формування результатів і перетворення даних між етапами.

Юніт-тести повинні бути частиною інженерної документації проєкту. Для AI-агента вони мають виконувати роль машинно-читабельного контракту: що саме дозволено змінювати, яка поведінка вважається правильною і які регресії неприпустимі.

## 2. Що вважати юніт-тестом у цьому проєкті

Юніт-тестом у цьому проєкті варто вважати тест, який перевіряє маленьку частину логіки без запуску повного DP1/DP2 pipeline. Такий тест може створювати маленький `cv::Mat` у пам'яті, передавати його у функцію або клас і перевіряти результат.

Юніт-тест не повинен залежати від реальної камери, відеофайлу, Docker-контейнера, повного набору кадрів, файлового layout експерименту, мережі або конкретного робочого середовища. Якщо тест читає реальні кадри з директорії, запускає кілька модулів або перевіряє повний сценарій DP1 -> DP2 -> comparator, це вже не юніт-тест.

Для юніт-тестів потрібно надавати перевагу синтетичним in-memory даним. Наприклад, маленькі матриці 5x5, 10x10 або 32x32 з контрольованими значеннями пікселів краще підходять для перевірки логіки, ніж реальні зображення з dataset.

## 3. Рекомендована класифікація тестів

У проєкті бажано відразу розділити тести за типами.

`unit` - швидкі юніт-тести на синтетичних даних без файлової системи і зовнішнього середовища.

`accuracy` або `regression` - перевірка алгоритмічного результату на фіксованих еталонних кадрах або коротких контрольних послідовностях.

`integration` - перевірка взаємодії кількох компонентів, наприклад DP1 з підготовленим frame source або перетворення результатів DP1 у формат, придатний для DP2.

`performance` - окрема категорія для часу обробки, стабільності швидкодії, пам'яті та throughput. Ці тести не повинні змішуватися з unit tests.

`system` або `e2e` - повні сценарії запуску pipeline, включно з Docker, наборами кадрів, конфігураціями, результатами та звітами.

## 4. Рекомендована структура директорій

Можна використати таку базову структуру:

```text
/tests
  /unit
    /dp1
    /dp2
  /accuracy
    /dp1
    /dp2
  /integration
    /dp1_dp2
    /runner
  /performance
    /dp1
    /dp2
  /fixtures
    /images
    /configs
    /expected
```

На першому етапі достатньо створити тільки `tests/unit` і мінімальний набір fixtures, якщо вони справді потрібні. Для чистих юніт-тестів fixtures з файлами краще не використовувати або використовувати мінімально.

Важливо не змішувати тести з production-кодом. Production-код має бути доступний тестам через library targets, а не через включення `.cpp` файлів напряму в тестові файли.


## 5. Політика тестових даних

Для unit tests основний стандарт - синтетичні дані, створені безпосередньо в тесті. Це зменшує залежність від файлової системи і полегшує розуміння очікуваного результату.

Для accuracy/regression tests можна використовувати маленькі fixtures. Вони мають бути стабільними, версіонованими і добре описаними. Не потрібно додавати великі datasets у репозиторій без окремого рішення.

Для performance tests потрібно мати окремо визначені datasets або input sequences. Результати performance tests не треба трактувати так само, як unit tests: падіння performance test може бути наслідком середовища, тому політика оцінки має бути окремою.

Локальні артефакти, створені AI-агентом або тестовими запусками, не повинні випадково потрапляти в git. Для цього потрібно мати правила в `.gitignore` і в інструкціях для агента.

## 6. Правила для assertions у CV-коді

Для простих integer-значень і малих синтетичних матриць можна використовувати точне порівняння.

Для floating-point результатів потрібно використовувати порівняння з допуском.

Для зображень і масок потрібно вибирати assertion відповідно до сенсу перевірки:

- точна рівність для повністю контрольованих синтетичних масок;
- кількість ненульових пікселів для перевірки площі;
- bounding box coordinates для перевірки локалізації;
- IoU для порівняння областей;
- norm або mean absolute difference для приблизного порівняння зображень;
- інваріанти, якщо точний результат не повинен бути частиною контракту.

Не варто тестувати OpenCV як бібліотеку. Тести мають перевіряти те, як код проєкту використовує OpenCV і які гарантії дає власна логіка.

## 7. Правила іменування тестів

Рекомендований стиль назв:

```text
FunctionOrClass_WhenCondition_ExpectedResult
```

Приклади:

```text
ComputeTileIndex_WhenSecondRowAndThirdColumn_ReturnsExpectedLinearIndex
ConvertTo8Bit_WhenInputIs16Bit_PreservesSizeAndScalesValues
ComputeResidual_WhenFrameValueIsLowerThanMedian_UsesConfiguredNegativeResidualPolicy
ExtractComponents_WhenMaskIsEmpty_ReturnsNoObjects
MapDp1Result_WhenObjectIsConfirmed_PreservesFrameIndexAndCenterPoint
```

Назва має пояснювати поведінку, а не просто повторювати назву функції. Це важливо для читабельності, для рев'ю і для AI-агента.

## 8. Правила для AI-агента

AI-агент не повинен додавати великі інтеграційні тести під виглядом юніт-тестів. Якщо тест читає реальні кадри, запускає process runner, Docker або повний pipeline, він має бути віднесений до integration/regression/system tests.

AI-агент має спочатку шукати testable unit. Якщо логіка не тестується через надто сильну прив'язку до runner-коду, агент має запропонувати мінімальне винесення логіки в окрему функцію або клас, а не тестувати через запуск всієї програми.

AI-агент не повинен змінювати очікувані результати тестів лише для того, щоб тести проходили. Якщо поведінка змінилася, потрібно явно пояснити, чи це виправлення помилки, зміна контракту або випадкова регресія.

AI-агент має відокремлювати локальні експериментальні файли від репозиторних fixtures. Тимчасові результати запусків не повинні додаватися в shared knowledge files або production-директорії без дозволу.



Такий набір не дасть повного покриття, але створить основу для безпечного рефакторингу і для подальшої роботи AI-агента.

## 9. Рекомендовані правила для TESTING_POLICY.md

У `TESTING_POLICY.md` варто зафіксувати такі положення:

- GoogleTest є основним фреймворком для C++ unit tests.
- CTest використовується як стандартний механізм запуску тестів через CMake.
- Unit tests мають бути швидкими, детермінованими і незалежними.
- Unit tests не повинні використовувати реальну камеру, Docker, мережу або повний dataset.
- Для CV unit tests перевага надається синтетичним `cv::Mat` у пам'яті.
- Accuracy/regression tests і performance tests зберігаються окремо від unit tests.
- Зміна expected result вимагає пояснення причини.
- Новий алгоритмічний код має супроводжуватися тестами для нормальних, граничних і помилкових сценаріїв.
- AI-агент не має права підміняти юніт-тести інтеграційними тестами без явного маркування.
