# Відкладений план майбутньої реалізації МКМФ

Статус: відкладено.

Цей файл зберігає майбутні кроки реалізації коду для МКМФ. Ці кроки не входять
до поточної задачі. Поточна задача зупиняється на аналізі Технічного завдання,
узгодженні з Project Knowledge та підготовці `специфікація МКМФ`.

## Передумови

Перед початком реалізації коду:
- `специфікація МКМФ` має існувати в canonical DP1 knowledge;
- DP1 canonical index має вести до цієї специфікації;
- `dp1.stage.radiometric_correction` має прив'язувати `inverse_median` до
  `специфікація МКМФ`;
- canonical-конфігурація `C` має визначати параметри МКМФ та значення за
  замовчуванням;
- створення тестів має бути явно погоджене, якщо автоматизовані тести потрібні.

## 1. Знайти точку інтеграції

Прочитати поточну ціль реалізації та визначити найменшу коректну точку
інтеграції МКМФ:
- DP1 radiometric stage або еквівалентну межу модуля;
- представлення типів кадру;
- шлях runtime-конфігурації;
- наявні profiling/context helpers;
- наявну модель `reset`/lifecycle.

Не виконувати широкого рефакторингу.

## 2. Визначити API реалізації

Очікувані поняття реалізації:
- `TemporalMedianConfig`;
- `TemporalMedianMode`;
- `OutputDynamicRangeMode`;
- `TemporalMedianFilter`;
- `reset(width, height, pixel_type)`;
- `processFrame(...) -> valid/invalid result`.

Конкретний API може відрізнятися, якщо архітектура проєкту вже має кращий
інтерфейс етапу.

## 3. Реалізувати стан і буфери

Обов'язкова поведінка:
- циклічний буфер для 3 або 5 відібраних кадрів;
- попередньо виділений буфер медіани;
- відсутність динамічних алокацій у `processFrame`;
- буфери виділяються під час construction або `reset`;
- явний стан для frame counter, selected-frame counter, warm-up status та
  останньої валідної медіани.

## 4. Реалізувати часову логіку

Обов'язкова поведінка:
- початок лічильника кадрів має бути явно зафіксований;
- правило відбору кадру відповідає погодженій специфікації, очікувана форма:
  `t % stride == 0`;
- медіана оновлюється тільки на відібраних кадрах;
- після warm-up residual формується для кожного вхідного кадру;
- кадри, що не потрапили до буфера, використовують останню валідну медіану;
- до warm-up результат невалідний.

## 5. Реалізувати ядра медіани

Обов'язкові ядра:
- `FixedK3` з окремим `median3`;
- `FixedK5` з окремою sorting network `median5`;
- без generic arbitrary-K path у цьому scope;
- без centered-window mode.

## 6. Реалізувати типи даних

Обов'язкова підтримка:
- вхід `uint8`;
- вхід `uint16`;
- медіанний кадр у фактичному форматі вхідного кадру;
- residual `int16` для `uint8`;
- residual `int32` для `uint16`.

Розширення діапазону належить до віднімання residual, а не до обчислення
медіани.

## 7. Реалізувати приведення виходу

Внутрішній вихід pipeline за замовчуванням - signed residual.

Користувацький або compatibility output може використовувати явні режими
приведення:
- `RawSigned`;
- `ClipToInputRange`;
- `ShiftToPositive`;
- `ScaleToInputRange`.

Приведення є окремим проходом і не має бути приховане всередині обчислення
медіани.

## 8. Додати profiling hooks

Профілювати окремо:
- оновлення медіани на відібраному кадрі;
- формування residual;
- приведення виходу;
- сумарний час етапу;
- вартість optional median-frame output.

## 9. Валідувати після погодження

Якщо тести погоджено, реалізувати focused checks для:
- еталонної медіани через full sort;
- `FixedK3`, `stride = 1, 2, 3`;
- `FixedK5`, `stride = 1, 2, 3`;
- causal window;
- hold-last-median behavior;
- невалідного результату до warm-up;
- `uint8 -> int16`;
- `uint16 -> int32`;
- усіх output conversion modes;
- стабільності на довгій послідовності;
- відсутності hot-loop allocation, якщо це можна інструментувати.

Без погодження тестів валідація обмежується code reading, build та ручними
sanity checks, які не додають test files або fixtures.
